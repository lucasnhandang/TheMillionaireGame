\subsection{Communication Protocol Design}

\subsubsection{Overview}

The Millionaire Game application employs the Transmission Control Protocol (TCP) as its underlying transport layer protocol for all client-server communications. TCP, defined in RFC 793, provides a reliable, connection-oriented, full-duplex communication channel between networked hosts.

\textbf{TCP Fundamentals:}
TCP operates on the transport layer (Layer 4) of the OSI model and provides several critical guarantees for application-layer protocols:
\begin{itemize}
    \item \textbf{Reliable Delivery}: TCP uses acknowledgments (ACKs), sequence numbers, and retransmission mechanisms to ensure all data segments arrive at the destination without loss or corruption
    \item \textbf{Ordered Delivery}: Segments are reassembled in the correct order at the receiver, regardless of network routing variations
    \item \textbf{Connection-Oriented}: Establishes a stateful connection through a three-way handshake (SYN, SYN-ACK, ACK) before data transmission
    \item \textbf{Flow Control}: Implements sliding window protocol to prevent sender from overwhelming receiver
    \item \textbf{Congestion Control}: Dynamically adjusts transmission rate based on network conditions
\end{itemize}

\textbf{Advantages for Game Protocol:}
The selection of TCP over UDP for this application is justified by several key requirements:
\begin{enumerate}
    \item \textbf{Data Integrity}: Game state synchronization (questions, answers, scores) requires 100\% accuracy. TCP's error-checking and retransmission ensure no data corruption.
    \item \textbf{Sequential Operations}: Game flow depends on strict ordering—questions must be delivered sequentially, answers must be processed in order. TCP's in-order delivery guarantee eliminates the need for application-layer reordering logic.
    \item \textbf{Simplified Development}: TCP's reliability eliminates complex application-layer error handling, reducing development complexity and potential bugs.
    \item \textbf{Session Management}: TCP's connection state naturally maps to game sessions, simplifying authentication and state tracking.
    \item \textbf{Acceptable Latency}: Turn-based gameplay (30-second question timers) tolerates TCP's slightly higher latency compared to UDP, making reliability more valuable than raw speed.
\end{enumerate}

The implementation utilizes POSIX socket API with \texttt{SOCK\_STREAM} type (indicating TCP) for both server and client components, ensuring cross-platform compatibility across Unix-like systems.

\subsubsection{Message Format}

All communication employs JSON (JavaScript Object Notation, RFC 8259) as the serialization format, with newline (\texttt{\textbackslash n}) as the message delimiter for stream framing. This design enables simple parsing while supporting nested data structures.

\textbf{Request Format (Client → Server):}
\begin{lstlisting}[language=json,basicstyle=\small\ttfamily]
{
  "requestType": "REQUEST_TYPE",
  "data": {
    /* Request-specific fields */
  }
}
\end{lstlisting}

\textbf{Response Format (Server → Client):}
\begin{lstlisting}[language=json,basicstyle=\small\ttfamily]
{
  "responseCode": 200,
  "data": {
    /* Response-specific fields */
  }
}
\end{lstlisting}

\textbf{Error Format:}
\begin{lstlisting}[language=json,basicstyle=\small\ttfamily]
{
  "responseCode": 4xx/5xx,
  "message": "Human-readable error description"
}
\end{lstlisting}

\textbf{Stream Handling:}
The protocol implements a custom \texttt{StreamHandler} class for managing TCP byte streams:
\begin{itemize}
    \item \textbf{Buffering}: 4KB default buffer with dynamic resizing for large messages
    \item \textbf{Framing}: Messages delimited by newline (\texttt{\textbackslash n}), allowing multiple messages per TCP segment
    \item \textbf{Partial Read Handling}: Buffer accumulates incomplete messages until full delimiter received
    \item \textbf{Timeout Management}: Configurable read/write timeouts using \texttt{SO\_RCVTIMEO} and \texttt{SO\_SNDTIMEO}
\end{itemize}

\subsubsection{Protocol Specifications}

\paragraph{Authentication and Session Management}

\textbf{LOGIN}: Authenticate user credentials and establish session.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
Request:  {"requestType":"LOGIN","data":{"username":<string>,"password":<string>}}
Response: {"responseCode":200,"data":{"authToken":<string>,"username":<string>,"role":<string>}}
Errors:   400(INVALID_DATA), 401(LOGIN_FAILED), 403(FORBIDDEN)
\end{lstlisting}

\textbf{REGISTER}: Create new user account with password validation.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
Request:  {"requestType":"REGISTER","data":{"username":<string>,"password":<string>}}
Response: {"responseCode":201,"data":{"message":<string>}}
Errors:   400(INVALID_DATA), 409(CONFLICT), 410(WEAK_PASSWORD)
\end{lstlisting}

Password requirements: ≥8 characters, ≥1 uppercase, ≥1 lowercase, ≥1 digit.

\textbf{LOGOUT}: Terminate session and disconnect.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
Request:  {"requestType":"LOGOUT","data":{"authToken":<string>}}
Response: {"responseCode":200,"data":{"message":<string>}}
\end{lstlisting}

\paragraph{Game Flow}

\textbf{START}: Initiate new game session with unique \texttt{gameId}.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
Request:  {"requestType":"START","data":{"authToken":<string>,"overrideSavedGame":<bool>}}
Response: GAME_START notification → QUESTION_INFO for first question
Errors:   402(AUTH_ERROR), 405(USER_ALREADY_IN_GAME), 412(INVALID_GAME_STATE)
\end{lstlisting}

\textbf{ANSWER}: Submit answer to current question with scoring validation.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
Request:  {"requestType":"ANSWER","data":{"authToken":<string>,"gameId":<int>,
           "questionNumber":<int>,"answerIndex":<int>}}
Response: {"responseCode":200,"data":{"correct":<bool>,"questionNumber":<int>,
           "pointsEarned":<int>,"totalScore":<int>,"status":<string>}}
Errors:   402(AUTH_ERROR), 406(USER_NOT_IN_GAME), 408(QUESTION_TIMEOUT),
          412(INVALID_GAME_STATE), 422(UNPROCESSABLE_DATA)
\end{lstlisting}

Scoring: Points = $\max(0, 30 - \text{timeElapsed} - 5 \times \text{lifelinesUsed})$

\textbf{LIFELINE}: Request assistance using 50/50, PHONE, or AUDIENCE.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
Request:  {"requestType":"LIFELINE","data":{"authToken":<string>,"gameId":<int>,
           "questionNumber":<int>,"lifelineType":<string>}}
Response: LIFELINE_INFO notification with assistance data
Errors:   402(AUTH_ERROR), 406(USER_NOT_IN_GAME), 407(LIFELINE_ALREADY_CHOSEN),
          412(INVALID_GAME_STATE), 422(UNPROCESSABLE_DATA)
\end{lstlisting}

Lifeline processing delays: 50/50 (5s), AUDIENCE (5s), PHONE (10s). Each lifeline imposes 5-point penalty and is single-use per game.

\textbf{GIVE\_UP}: Forfeit game and collect current winnings.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
Request:  {"requestType":"GIVE_UP","data":{"authToken":<string>,"gameId":<int>,
           "questionNumber":<int>}}
Response: {"responseCode":200,"data":{"status":<string>,"finalPrize":<int>,
           "finalScore":<int>,"questionNumber":<int>}}
Errors:   402(AUTH_ERROR), 406(USER_NOT_IN_GAME), 412(INVALID_GAME_STATE)
\end{lstlisting}

\textbf{RESUME}: Continue auto-saved game after disconnection.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
Request:  {"requestType":"RESUME","data":{"authToken":<string>}}
Response: {"responseCode":200,"data":{"questionNumber":<int>,"currentPrize":<int>,
           "totalScore":<int>,"lifelinesUsed":[<string>]}}
          → QUESTION_INFO notification
Errors:   402(AUTH_ERROR), 404(NOT_FOUND), 405(USER_ALREADY_IN_GAME)
\end{lstlisting}

\paragraph{Social Features}

\textbf{LEADERBOARD}: Retrieve global or friend rankings.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
Request:  {"requestType":"LEADERBOARD","data":{"authToken":<string>,"type":<string>,
           "page":<int>,"limit":<int>}}
Response: {"responseCode":200,"data":{"rankings":[{"rank":<int>,"username":<string>,
           "finalQuestionNumber":<int>,"totalScore":<int>,"isWinner":<bool>},...],
           "total":<int>,"page":<int>}}
\end{lstlisting}

Ranking: Primary by \texttt{finalQuestionNumber} (desc), secondary by \texttt{totalScore} (desc).

\textbf{FRIEND\_STATUS}: Query online/offline/in-game status of friends.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
Request:  {"requestType":"FRIEND_STATUS","data":{"authToken":<string>}}
Response: {"responseCode":200,"data":{"friends":[{"username":<string>,
           "status":<string>},{"username":<string>,"status":<string>}]}}
\end{lstlisting}

\textbf{ADD\_FRIEND / ACCEPT\_FRIEND / DECLINE\_FRIEND}: Manage friend relationships.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
ADD:      {"requestType":"ADD_FRIEND","data":{"authToken":<string>,"friendUsername":<string>}}
ACCEPT:   {"requestType":"ACCEPT_FRIEND","data":{"authToken":<string>,"friendUsername":<string>}}
DECLINE:  {"requestType":"DECLINE_FRIEND","data":{"authToken":<string>,"friendUsername":<string>}}
Errors:   402(AUTH_ERROR), 404(NOT_FOUND), 409(CONFLICT), 422(UNPROCESSABLE_DATA)
\end{lstlisting}

\textbf{CHAT}: Send message to online/offline user (stores for offline delivery).
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
Request:  {"requestType":"CHAT","data":{"authToken":<string>,"recipient":<string>,
           "message":<string>}}
Response: {"responseCode":200,"data":{"message":<string>}}
Errors:   400(INVALID_DATA), 402(AUTH_ERROR), 404(NOT_FOUND), 422(UNPROCESSABLE_DATA)
\end{lstlisting}

\paragraph{User Information}

\textbf{USER\_INFO}: Retrieve player profile and statistics.

\end{lstlisting}

\textbf{CHANGE\_PASS}: Update account password with validation.

\paragraph{Admin Operations}

Admin requests use identical \texttt{authToken} authentication but require \texttt{role="admin"} validation on server. Authorization failure returns 403 (FORBIDDEN).

\textbf{ADD\_QUES}: Insert new question into database.
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]

          422(UNPROCESSABLE_DATA)
\end{lstlisting}

\textbf{BAN\_USER}: Permanently disable user account (irreversible).

\textbf{Error Response Structure:}
All errors return JSON with \texttt{responseCode} and human-readable \texttt{message}:
\begin{lstlisting}[language=json,basicstyle=\footnotesize\ttfamily]
{"responseCode":422,"message":"Invalid answerIndex: must be 0-3"}
\end{lstlisting}

\textbf{Client Error Handling Strategy:}
\begin{itemize}
    \item \textbf{4xx errors}: Client-side issue—validate input and retry only after correcting request
    \item \textbf{5xx errors}: Server-side issue—implement exponential backoff retry (max 3 attempts)
    \item \textbf{401/402}: Redirect to login screen and clear invalid credentials
    \item \textbf{429}: Respect rate limits with exponential backoff (starting at 1s)
    \item \textbf{408}: Treat as game loss—no retry, display safe checkpoint prize
\end{itemize}

\subsubsection{Game Mechanics}

\paragraph{Scoring System}
\begin{itemize}
    \item \textbf{Base Points}: 30 points maximum per question
    \item \textbf{Time Penalty}: -1 point per second elapsed (30s timer)
    \item \textbf{Lifeline Penalty}: -5 points per lifeline used (cumulative)
    \item \textbf{Formula}: $\text{points} = \max(0, 30 - t_{\text{elapsed}} - 5n_{\text{lifelines}})$
    \item \textbf{Total Score}: Sum of points from all correct answers up to final question
\end{itemize}

\paragraph{Safe Checkpoints}
\begin{itemize}
    \item \textbf{Checkpoints}: Questions 5, 10, 15 (corresponding to prize milestones)
    \item \textbf{Failure Behavior}: Wrong answer or timeout → receive prize from last passed checkpoint
    \item \textbf{Pre-Checkpoint Failure}: Failing before Q5 → prize = 0, score = 0
    \item \textbf{GIVE\_UP}: Voluntary quit → receive \textit{current} prize (not checkpoint)
\end{itemize}

\paragraph{Session Management}
\begin{itemize}
    \item \textbf{Game ID}: Unique identifier per game session to prevent cross-game confusion
    \item \textbf{Auto-Save}: Server persists game state on unexpected disconnection
    \item \textbf{Reconnection}: Client can RESUME saved game or START new (with override flag)
    \item \textbf{State Lifecycle}: Active game → (disconnect) → Auto-saved → RESUME/override
    \item \textbf{State Clearing}: Game ends (won/lost/quit) → state cleared → can START new
\end{itemize}

\paragraph{Lifeline Mechanics}
\begin{itemize}
    \item \textbf{50/50}: Eliminates 2 incorrect options, returns indices of remaining 2 options
    \item \textbf{PHONE}: Friend suggestion with confidence level (high/medium/low)
    \item \textbf{AUDIENCE}: Poll distribution across 4 options (percentages sum to 100)
    \item \textbf{Processing Delays}: 50/50 (5s), AUDIENCE (5s), PHONE (10s)—timer continues during delay
    \item \textbf{Single-Use}: Each lifeline can only be used once per game
\end{itemize}

\subsubsection{Rate Limiting and Security}

\textbf{Rate Limits (per IP address):}
\begin{itemize}
    \item General requests: 100 requests/minute
    \item Authentication (LOGIN/REGISTER): 5 requests/minute
    \item Game actions: 30 requests/minute per authenticated user
    \item Admin requests: 50 requests/minute per admin account
\end{itemize}

\textbf{Violation Handling:}
\begin{itemize}
    \item First violation: Return 429 error with retry-after header
    \item Repeated violations: Temporary IP ban (5-15 minutes)
    \item Severe abuse: Permanent IP ban
\end{itemize}

\textbf{Security Measures:}
\begin{itemize}
    \item \textbf{Password Storage}: bcrypt hashing with per-user salt (implemented in database layer)
    \item \textbf{Token Management}: Server maintains \texttt{authToken} → username mapping with expiration
    \item \textbf{Input Validation}: JSON schema validation before business logic processing
    \item \textbf{SQL Injection Prevention}: Parameterized queries via libpq prepared statements
    \item \textbf{Connection Timeout}: Idle connections terminated after 300s to prevent resource exhaustion
\end{itemize}
